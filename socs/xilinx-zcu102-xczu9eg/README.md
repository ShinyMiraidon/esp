# Xilinx ZCU102 Flow Notes

The ZCU102 flow is different from the regular fabric-only Xilinx FPGA flow
because this board boots through the Zynq UltraScale+ MPSoC processing system
(PS). The ESP design is still synthesized into the programmable logic (PL), but
the boot chain, device tree, U-Boot, Linux image, and optional JTAG boot flow are
generated through `utils/zynq`.

## Required Environment

Vivado 2019.2 and 2023.2 can both be used for PL synthesis. Choose the version
that works best with the build host and use it for `make vivado-syn`. If
switching synthesis versions, run `make vivado-distclean` first so that the
Vivado project is regenerated by the selected version.

The Zynq collateral must still be generated with Vivado 2019.2:

```sh
source /opt/Xilinx/Vivado/2019.2/settings64.sh
```

The Zynq build scripts in `utils/zynq` hard-check that `XILINX_VIVADO` contains
`2019.2` because `make zynq` uses the older Xilinx SDK/HSI flow. When synthesis
is run with Vivado 2023.2, switch to the Vivado 2019.2 environment before
running `make zynq`. Vivado 2023.2 does not emit the legacy `.hwdef` expected by
the SDK/HSI flow, so `make zynq` automatically generates a 2019.2-compatible PS
hardware handoff from the board's block-design Tcl. This does not rerun ESP
synthesis or replace the bitstream produced by Vivado 2023.2.

The build machine also needs the Zynq software toolchain pieces used by
`utils/zynq`, including:

- `vivado`, `xsct`, and `bootgen` from Vivado 2019.2
- `aarch64-linux-gnu-` cross tools
- host tools such as `gcc`, `dtc`, `make`, `tar`, and `wget`

## Normal Build Sequence

Run these commands from this directory:

```sh
cd socs/xilinx-zcu102-xczu9eg
make vivado-syn
make zynq
```

`make vivado-syn` builds the PL bitstream for `zynqmp_top_wrapper`.

`make zynq` requires that bitstream to already exist. It then invokes
the helper flow in `utils/zynq` with `BOARD=zcu102` and stages the Zynq boot
collateral under this board directory:

```text
socs/xilinx-zcu102-xczu9eg/zynq/zcu102/
```

The main generated outputs are:

- `socs/xilinx-zcu102-xczu9eg/zynq/zcu102/images/BOOT.bin`
- `socs/xilinx-zcu102-xczu9eg/zynq/zcu102/images/bitstream.bin`
- `socs/xilinx-zcu102-xczu9eg/zynq/zcu102/images/Image`
- `socs/xilinx-zcu102-xczu9eg/zynq/zcu102/images/system.dtb`
- `socs/xilinx-zcu102-xczu9eg/zynq/zcu102/sd-card/`

The `sd-card` directory is a staging tree for the files that should be copied to
the SD card boot/root partitions. Its `boot/` directory goes to the FAT32 boot
partition, and its `root/` directory contains the Linux root filesystem for the
ext4 root partition. The root filesystem tarball is downloaded by the scripts in
`utils/zynq` if it is not already present.

Useful partial targets:

```sh
make zynq-sdk
make zynq-u-boot
make zynq-linux
make zynq-distclean
```

`make zynq-u-boot`, `make zynq-linux`, and `make zynq` pass
`HOST_EXTRACFLAGS=-fcommon` into the old Xilinx U-Boot build. This is needed on
newer host GCC versions, where U-Boot's bundled DTC otherwise fails with a
multiple-definition error for `yylloc`.

The ESP Zynq targets also unset `LD_LIBRARY_PATH` only for the recursive
`utils/zynq` software-build commands. This prevents the Vivado library path from
overriding host libraries while building the legacy Zynq software, without
changing the calling shell or the Vivado hardware-handoff environment.

## Programming and Running

The regular Xilinx FPGA flow is centered on:

```sh
make fpga-program
make fpga-run
```

That path assumes ESPLink is reachable from the host through the FPGA fabric.
`make fpga-run` builds `tools/esplink`, connects to `ESPLINK_IP:ESPLINK_PORT`,
loads the boot ROM and test program, and resets the ESP SoC.

ZCU102 is not wired that way. Ethernet is on the Zynq PS, not as a fabric-side
ESPLink endpoint, so the board Makefile leaves `ESPLINK_IP` empty. For ZCU102,
prepare the SD card from the staged Zynq output first:

```text
socs/xilinx-zcu102-xczu9eg/zynq/zcu102/sd-card/boot/
socs/xilinx-zcu102-xczu9eg/zynq/zcu102/sd-card/root/
```

Copy the boot files to the root of the FAT32 boot partition:

```sh
cp -a zynq/zcu102/sd-card/boot/* <mounted-boot-partition>/
```

Copy the contents of the staged root filesystem to the root of the ext4 root
partition:

```sh
sudo rsync -aHAX zynq/zcu102/sd-card/root/ <mounted-rootfs-partition>/
```

For ZCU102, `make zynq` also patches the generated device tree with
`disable-wp;` for `sdhci1`. Without this, Linux may report `mmcblk0` as
read-only and panic while mounting `root=/dev/mmcblk0p2 rw` with `error -30`.

`make zynq` also reserves PS DDR physical `0x20000000-0x5fffffff` for ESP with a
`reserved-memory` `no-map` node. The ZCU102 wrapper maps ESP's 1 GiB DRAM window
`0x80000000-0xbfffffff` onto that reserved PS DDR range, so Linux should no
longer claim the memory used for ESP bare-metal or Linux payloads.

The current JTAG flow is not a replacement for the SD card. On ZCU102, the
standard `make fpga-program` target is an alias for `make zynq-jtag-boot`. Use
either target after the Zynq images have been built and after the SD card has
been prepared and inserted.

The JTAG target connects through `hw_server`:

```sh
make fpga-program FPGA_HOST=<hw_server-host> XIL_HW_SERVER_PORT=<hw_server-port>
```

It programs the PL bitstream and downloads PMU firmware, FSBL, device tree,
U-Boot, and ARM Trusted Firmware. The script does not currently download the
Linux kernel or root filesystem by JTAG, so U-Boot still needs the SD card to
load Linux and continue the boot. The generated ZynqMP `uEnv.txt` skips the
U-Boot `fpga load` step when `modeboot=jtagboot`, because XSCT has already
programmed the PL. In SD boot mode, U-Boot still loads `bitstream.bin` from the
boot partition.

The ESP Zynq U-Boot build forces the default boot command to `run sdboot`.
Without that override, ZynqMP JTAG boot sets `modeboot=jtagboot`, and U-Boot can
try PXE/DHCP before it reaches the SD-card `uEnv.txt`. If an older U-Boot image
gets stuck at PHY auto-negotiation, interrupt autoboot and run:

```text
run sdboot
```

The ESP `make zynq` wrapper patches the generated U-Boot configuration before
the SD-card staging step, so rerunning `make zynq` is enough to pick this up.

The same wrapper appends `maxcpus=1` to the generated ZCU102 `uEnv.txt`
`bootargs` line. Without this, the 2018.2 ZynqMP Linux kernel can stall during
SMP clock-update broadcast while setting time from the RTC.

After Linux reaches the serial console login prompt, use the default root
account from the `utils/zynq` root filesystem:

```text
login: root
password: SLD#xil.33
```

## Run ESP Through Zynq PS Linux

ZCU102 uses a PS-side loader instead of ESPLink-over-fabric Ethernet. The loader
is checked in under:

```text
socs/xilinx-zcu102-xczu9eg/ps/
```

After copying the `ps/` directory to the Zynq Linux root filesystem, build the
tools there if it has a compiler:

```sh
make -C ps
```

Or cross-build them on the host with an AArch64 cross compiler:

```sh
make -C ps cross
```

Install `esp_peek` and `esp_load_bootrom_zynq` somewhere in the Zynq Linux run
directory. The default `make fpga-run` backend expects them in `.` on the PS,
but the paths can be overridden.

From this board directory, run the bare-metal systest payload with:

```sh
make fpga-run ZYNQ_PS_HOST=<zynq-ps-host>
```

Run the ESP Linux payload with:

```sh
make fpga-run-linux ZYNQ_PS_HOST=<zynq-ps-host>
```

`ZYNQ_PS_HOST` may include a user, such as `root@<zynq-ps-host>`. If no user is
included, the flow uses `ZYNQ_PS_USER`, which defaults to `root`. The SSH port
defaults to `SSH_PORT`, then `22`. `SSH_IP` and `PS_HOST` are accepted as host
aliases, but `ZYNQ_PS_HOST` is the preferred ZCU102 name.

The Zynq PS loader supports these variables:

| Variable | Purpose |
| --- | --- |
| `ZYNQ_PS_HOST` | PS Linux SSH host |
| `ZYNQ_PS_USER` | SSH user, default `root` |
| `ZYNQ_PS_SSH_PORT` | SSH port, default from `SSH_PORT` or `22` |
| `ZYNQ_PS_RUN_DIR` | Remote directory for `prom.bin`, payload, and tools |
| `ZYNQ_PS_SSH_OPTS` | Extra SSH/SCP options |
| `ZYNQ_PS_SSH_RUN_OPTS` | Extra SSH options for the remote run command |
| `ZYNQ_PS_SUDO` | Prefix for `/dev/mem` commands, usually empty for root |
| `ZYNQ_PS_PEEK` | Remote path to `esp_peek` |
| `ZYNQ_PS_LOADER` | Remote path to `esp_load_bootrom_zynq` |
| `ZYNQ_PS_LOADER_CPU` | CPU profile, default `$(CPU_ARCH)` |
| `ZYNQ_PS_LOADER_OPTS` | Extra loader options, default CPU and DRAM path options |
| `ZYNQ_PS_DRAM_PATH` | DRAM load path, `esp` or `ps-ddr`, default `esp` |
| `ZYNQ_PS_WAKE_ADDR` | Wake CSR read before loading |

### Dropbear Host-Key Compatibility

The Zynq root filesystem uses Dropbear 2016.74. If it has only an RSA host key,
current host operating systems may reject the connection with this error:

```text
Unable to negotiate: no matching host key type found. Their offer: ssh-rsa
```

The ZCU102 commands in `utils/make/fpga.mk` pass `-q` to `ssh` and `scp` by
default, so this diagnostic is shown only if `-q` is temporarily removed while
troubleshooting.

Here, `ssh-rsa` refers to the legacy RSA/SHA-1 signature algorithm, not to all
uses of RSA keys. Rather than weakening the host's SSH policy, log in to the
board through its serial console and create an ECDSA P-256 host key once:

```sh
mkdir -p /etc/dropbear
if [ ! -f /etc/dropbear/dropbear_ecdsa_host_key ]; then
  umask 077
  dropbearkey -t ecdsa -s 256 \
    -f /etc/dropbear/dropbear_ecdsa_host_key
fi
reboot
```

Do not overwrite an existing host key, because doing so changes the board's SSH
identity. After rebooting, Dropbear automatically loads the key and current
OpenSSH clients can negotiate `ecdsa-sha2-nistp256` without enabling
RSA/SHA-1 compatibility.

The most useful overrides are:

```sh
make fpga-run \
  ZYNQ_PS_HOST=<zynq-ps-host> \
  ZYNQ_PS_RUN_DIR=<remote-run-dir> \
  ZYNQ_PS_PEEK=<path-to-esp_peek> \
  ZYNQ_PS_LOADER=<path-to-esp_load_bootrom_zynq>
```

For direct PS DDR comparisons, switch to the backing-memory path with:

```sh
make fpga-run ZYNQ_PS_HOST=<zynq-ps-host> ZYNQ_PS_DRAM_PATH=ps-ddr
```

If the PS login is not root, set `ZYNQ_PS_USER` and `ZYNQ_PS_SUDO=sudo`, since
the loader needs `/dev/mem` access.

The Makefile copies `soft-build/<cpu>/prom.bin` and the selected payload to
`ZYNQ_PS_RUN_DIR`, performs two wake reads through `esp_peek`, and then runs:

```sh
./esp_load_bootrom_zynq prom.bin --cpu <cpu> --dram-via-esp --dram-image <payload>
```

The loader supports `ariane`, `ibex`, and `leon3` CPU profiles. It does not
verify payload readback unless `--verify` is passed explicitly. Bootrom
programming still uses ESP's big-endian 32-bit word packing through the ESP
aperture. DRAM `.bin` payload programming now defaults to the same ESP-aperture
packed-word path. Use `ZYNQ_PS_DRAM_PATH=ps-ddr` to load byte-for-byte into the
reserved PS DDR backing window at `0x20000000` for comparison, or add
`--dram-word-pack` with `--dram-binary-word-order <be|le>` to force packed-word
direct-DDR mode.

The profile addresses are:

| CPU | Bootrom address | ESP payload aperture | PS DDR backing address | Reset CSR | Wake CSR |
| --- | --- | --- | --- | --- | --- |
| Ariane | `0x0400010000` | `0x0480000000` | `0x0000000020000000` | `0x0460000400` | `0x0460090384` |
| Ibex | `0x0400000080` | `0x0480000000` | `0x0000000020000000` | `0x0460000400` | `0x0460090384` |
| LEON3 | `0x0400000000` | `0x0440000000` | `0x0000000020000000` | `0x0480000400` | `0x0480090384` |

## Board-Specific Notes

- The Vivado part is `xczu9eg-ffvb1156-2-e`.
- Hardware manager may report the programmed device as `xczu9_0`; the
  constraints include `PROGRAM_PART_ALIASES=xczu9` so programming checks can
  match the shorter device name.
- The ZCU102 top level is `zynqmp_top_wrapper`, which wraps the ESP top module
  and instantiates/connects the ZynqMP PS.
- Simulation of the full Zynq wrapper is not supported because the PS is not
  modeled. `make sim` can still elaborate the ESP-side testbench.
